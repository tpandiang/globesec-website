EC2Fundamental
Q1.An application runs a large in-memory cache and needs far more RAM than CPU. Which EC2 instance family fits best?
AC family (compute optimized)
BI family (storage optimized)
CT3 (burstable)
DR family (memory optimized)
✓ Correct: D. R family (memory optimized)

How to think about it: Memorise the family letters: R=RAM, C=CPU, M=balanced, I=local I/O, G=GPU, T=burstable.

Why D is correct: R instances have a high memory-to-vCPU ratio, built for in-memory caches and databases.

Why the others are wrong:
A) C family (compute optimized) — C is for CPU-heavy work such as batch processing or encoding, not large memory.
B) I family (storage optimized) — I is for very fast local NVMe instance storage (high I/O), not RAM.
C) T3 (burstable) — T3 gives a CPU baseline with burst credits; it is for spiky, light workloads.
EC2Fundamental
Q2.A big-data job must finish as fast as possible and needs the lowest network latency and highest throughput between its instances. Which placement group strategy should you use?
ASpread
BNo placement group, across three AZs
CCluster
DPartition
✓ Correct: C. Cluster

How to think about it: Lowest latency between nodes = everything close together = Cluster (same rack, same AZ).

Why C is correct: Cluster packs instances close together in one AZ, giving low latency and high bandwidth (with Enhanced Networking). The trade-off: a rack failure hits every instance.

Why the others are wrong:
A) Spread — Spread puts each instance on separate hardware for availability. This adds distance, not speed.
B) No placement group, across three AZs — Spreading across AZs adds latency between instances, the opposite of what is needed.
D) Partition — Partition separates groups of instances onto different racks for fault isolation in big distributed systems.
EC2Fundamental
Q3.A spread placement group is used for a small set of critical instances. What is its key limit?
AAt most 7 running instances per Availability Zone per group
BOnly one instance type is allowed in the group
CIt must stay inside a single Availability Zone
DAt most 100 instances per Availability Zone
✓ Correct: A. At most 7 running instances per Availability Zone per group

How to think about it: Spread = maximum isolation, so it is small: 7 running instances per AZ per group.

Why A is correct: Each instance sits on distinct hardware, which caps a spread group at 7 per AZ. It can span several AZs.

Why the others are wrong:
B) Only one instance type is allowed in the group — Spread does not restrict you to one instance type.
C) It must stay inside a single Availability Zone — That describes cluster placement groups. Spread groups can span AZs.
D) At most 100 instances per Availability Zone — Hundreds of instances is the partition strategy's scale, not spread's.
EC2Advanced
Q4.You are deploying Cassandra on hundreds of instances. A rack failure may take down a group of nodes but must not affect the others, and the application should know which rack each node is on. Which placement strategy fits?
ACluster placement group
BSpread placement group
CDedicated Hosts with host affinity
DPartition placement group
✓ Correct: D. Partition placement group

How to think about it: Hundreds of nodes, rack awareness, HDFS/HBase/Cassandra/Kafka = Partition.

Why D is correct: Partitions use separate racks (up to 7 per AZ, hundreds of instances), and each instance can read its partition number from instance metadata for rack-aware replication.

Why the others are wrong:
A) Cluster placement group — Cluster puts everything on the same hardware, so one rack failure can take down the whole ring.
B) Spread placement group — Spread isolates single instances but is capped at 7 per AZ, far too small for hundreds of nodes.
C) Dedicated Hosts with host affinity — Host affinity is for licensing and placement on a specific host, not rack-level fault domains.

Q5.A vendor licenses its database per physical CPU socket and core. The company needs to see the sockets and cores and keep instances on the same physical server after a reboot. What should it use?
AConvertible Reserved Instances
BDedicated Instances
CSpot Instances
DDedicated Hosts
✓ Correct: D. Dedicated Hosts

How to think about it: Licensing tied to sockets or cores, or needing host affinity = Dedicated Hosts.

Why D is correct: A Dedicated Host is an entire physical server you control. You can see its sockets and cores and set host affinity, which bring-your-own-licence software needs.

Why the others are wrong:
A) Convertible Reserved Instances — Reserved Instances are a billing discount. They say nothing about the physical server.
B) Dedicated Instances — Dedicated Instances run on hardware no other customer uses, but they do not show you sockets or cores or give you host placement control.
C) Spot Instances — Spot is spare capacity that can be reclaimed, so it is unsuitable for a licensed database.

Q6.Which of these metrics does CloudWatch NOT collect for an EC2 instance by default?
ANetworkIn / NetworkOut
BMemory (RAM) utilization
CCPUUtilization
DStatusCheckFailed_System
✓ Correct: B. Memory (RAM) utilization

How to think about it: The hypervisor sees CPU, network, disk and status checks. It cannot see inside the guest OS, so RAM needs the CloudWatch agent.

Why B is correct: AWS cannot see memory use inside the guest OS. Install the CloudWatch agent to publish it as a custom metric.

Why the others are wrong:
A) NetworkIn / NetworkOut — Network bytes in and out are default EC2 metrics.
C) CPUUtilization — CPU utilization is a default EC2 metric.
D) StatusCheckFailed_System — Status check metrics are published by default.
EC2Advanced
Q7.If the underlying AWS hardware fails, a single EC2 instance must recover automatically and keep its private IP, Elastic IP and instance metadata. What should you configure?
AAn Auto Scaling group with min = max = 1
BA CloudWatch alarm on StatusCheckFailed_Instance with a reboot action
CA CloudWatch alarm on StatusCheckFailed_System with the EC2 recover action
DA Lambda function that takes an AMI and relaunches it
✓ Correct: C. A CloudWatch alarm on StatusCheckFailed_System with the EC2 recover action

How to think about it: System status check = AWS hardware. Instance recovery moves the same instance to new hardware and keeps its identity.

Why C is correct: The recover action restarts the same instance on healthy hardware and keeps its private, public and Elastic IPs, metadata and placement group. You can also notify an SNS topic.

Why the others are wrong:
A) An Auto Scaling group with min = max = 1 — An ASG replaces the instance with a brand-new one, which gets a new private IP and ID.
B) A CloudWatch alarm on StatusCheckFailed_Instance with a reboot action — The instance check covers problems inside the VM (OS or software). A reboot does not move the instance off failed hardware.
D) A Lambda function that takes an AMI and relaunches it — That creates a new instance with new IPs, and it is custom work the recover action already does.

A15 minutes
B2 minutes
C30 seconds
D1 hour
✓ Correct: B. 2 minutes

How to think about it: Spot = up to 90% off, but you get only a 2-minute interruption notice.

Q9.A Spot Fleet should launch from the pools with the most spare capacity, and among those choose the cheapest. Which allocation strategy is this?
AlowestPrice
Bdiversified
CcapacityOptimized
DpriceCapacityOptimized
✓ Correct: D. priceCapacityOptimized

How to think about it: AWS's recommended default is priceCapacityOptimized: capacity first, then price.

Why D is correct: It picks the pools with the most available capacity and then the lowest price among them. This lowers interruptions while keeping cost low, and it is recommended for most workloads.

Why the others are wrong:
A) lowestPrice — lowestPrice looks only at price, so it can land in shallow pools that are interrupted more often.
B) diversified — diversified spreads instances across all pools for availability. It does not rank by capacity then price.
C) capacityOptimized — capacityOptimized considers capacity only and ignores price.

HPCFundamental
Q11.A tightly coupled HPC simulation on Linux uses MPI and needs the lowest-latency communication between nodes, bypassing the operating system. Which network interface should you use?
AIntel 82599 VF
BElastic Network Adapter (ENA)
CElastic Fabric Adapter (EFA)
DA second ENI on each instance
✓ Correct: C. Elastic Fabric Adapter (EFA)

How to think about it: MPI + tightly coupled + OS bypass = EFA. Plain high bandwidth = ENA.

Why C is correct: EFA is an enhanced ENA for HPC (Linux only). It supports MPI and bypasses the OS for low-latency, reliable traffic between nodes.

Why the others are wrong:
A) Intel 82599 VF — This is the legacy enhanced-networking option, limited to 10 Gbps.
B) Elastic Network Adapter (ENA) — ENA gives enhanced networking up to 100 Gbps, but it has no OS bypass for MPI.
D) A second ENI on each instance — Adding a network interface does not lower latency or add MPI support.

Q12.An HPC cluster needs a shared, distributed file system with millions of IOPS that can load data from and save results to Amazon S3. Which service fits?
AAmazon FSx for Windows File Server
BAmazon FSx for Lustre
CAmazon S3 mounted directly as a block device
DAmazon EFS
✓ Correct: B. Amazon FSx for Lustre

How to think about it: HPC file system + S3-backed = FSx for Lustre.

Why B is correct: Lustre is a parallel file system designed for HPC, scaling to millions of IOPS, and it links directly to an S3 bucket.

Why the others are wrong:
A) Amazon FSx for Windows File Server — This is an SMB file share for Windows applications, not HPC.
C) Amazon S3 mounted directly as a block device — S3 is object storage, not a POSIX file system or block device.
D) Amazon EFS — EFS is general-purpose NFS. Its performance is good but it is not tuned for HPC scratch workloads at Lustre scale.

Q14.One managed batch job must run across several EC2 instances at once (for example, an MPI job), with AWS handling scheduling and instance launches. Which option fits?
AAmazon ECS scheduled tasks
BAWS Batch multi-node parallel jobs
CAWS Lambda with reserved concurrency
DAn EventBridge schedule that starts On-Demand instances
✓ Correct: B. AWS Batch multi-node parallel jobs

How to think about it: One job spanning many instances, managed scheduling = AWS Batch multi-node parallel jobs.

Why B is correct: Batch can run a single job that spans several EC2 instances, and it launches and scales the compute environment for you.

Why the others are wrong:
A) Amazon ECS scheduled tasks — Scheduled tasks start containers on a timetable. They do not coordinate one job across several nodes.
C) AWS Lambda with reserved concurrency — Lambda invocations are independent, run for at most 15 minutes, and cannot form an MPI job.

Auto ScalingFundamental
Q15.You want an Auto Scaling group to keep average CPU around 40% with the least setup. Which policy should you use?
AScheduled action
BSimple scaling with a cooldown
CStep scaling
DTarget tracking scaling
✓ Correct: D. Target tracking scaling

How to think about it: "Keep a metric at X" = Target Tracking.

Why D is correct: Target tracking creates and manages the CloudWatch alarms itself and adds or removes capacity to hold the metric near its target.

Why the others are wrong:
A) Scheduled action — Scheduled actions change capacity at set times. They do not react to CPU.
B) Simple scaling with a cooldown — Simple scaling reacts to one alarm with a fixed adjustment. It is the legacy, coarse option.
C) Step scaling — Step scaling needs you to define the alarms and step adjustments yourself. It works, but it is more setup.

Q16.Traffic always jumps on Friday at 5 PM. How can you make sure at least 10 instances are running before then?
AA scheduled action that raises the minimum capacity to 10 just before 5 PM on Fridays
BA lifecycle hook on launch
CSuspend the AZRebalance process
DTarget tracking on CPU at 40%
✓ Correct: A. A scheduled action that raises the minimum capacity to 10 just before 5 PM on Fridays

How to think about it: Known, calendar-based pattern = Scheduled action.

Why A is correct: Scheduled actions change min, max or desired capacity at specific times, which suits predictable peaks.

Why the others are wrong:
B) A lifecycle hook on launch — Lifecycle hooks pause instances during launch or terminate. They do not schedule capacity.
C) Suspend the AZRebalance process — This only stops AZ rebalancing. It does not add capacity.
D) Target tracking on CPU at 40% — Target tracking reacts after load arrives, so instances may still be booting when the peak hits.

Q17.Before an Auto Scaling group terminates an instance, you must copy its application logs to S3. What should you use?
AA termination lifecycle hook
BReplace the instance's user data
CSuspend the Terminate process
DInstance scale-in protection
✓ Correct: A. A termination lifecycle hook

How to think about it: "Do something before in-service or before terminate" = Lifecycle hook.

Why A is correct: The hook holds the instance in Terminating:Wait so a script or Lambda can extract logs, then completes the lifecycle action.

Why the others are wrong:
B) Replace the instance's user data — User data runs at boot, not at termination.
C) Suspend the Terminate process — Suspending termination stops scale-in completely, which is not the goal.
D) Instance scale-in protection — Scale-in protection stops the instance being chosen for termination at all. It does not run a cleanup step.

Q18.You've published a new AMI in the launch template. All instances in the ASG must be replaced while at least 60% of capacity stays healthy. What is the native way to do this?
ASet desired capacity to 0 and then back to the original value
BStart an Instance Refresh with minimum healthy percentage set to 60%
CSuspend the ReplaceUnhealthy process and reboot every instance
DUpdate the launch template only
✓ Correct: B. Start an Instance Refresh with minimum healthy percentage set to 60%

How to think about it: Update the template, then Instance Refresh with a minimum healthy percentage and warm-up time.

Why B is correct: Instance Refresh replaces instances in batches using the new template, keeps at least 60% healthy, and respects the warm-up time.

Why the others are wrong:

C) Suspend the ReplaceUnhealthy process and reboot every instance — Rebooting does not change the AMI an instance runs.
D) Update the launch template only — Existing instances keep the old AMI. Only instances launched later use the new version.

Q19.Engineers are debugging instances that fail health checks. They want the ASG to stop terminating and replacing those instances for now, without changing anything else. What should they do?
ADelete the launch template
BSet desired capacity to 0
CSuspend the ReplaceUnhealthy process
DSuspend the AZRebalance process
✓ Correct: C. Suspend the ReplaceUnhealthy process

How to think about it: ASG processes (Launch, Terminate, HealthCheck, ReplaceUnhealthy, AZRebalance, …) can be suspended one by one.

Why C is correct: With ReplaceUnhealthy suspended, the group still marks instances unhealthy but does not terminate and replace them, so engineers can inspect them.

Why the others are wrong:
A) Delete the launch template — A group cannot run without its launch template, and this does not stop replacements.
B) Set desired capacity to 0 — This terminates every instance, including the ones they want to debug.
D) Suspend the AZRebalance process — AZRebalance only balances instances across AZs. Unhealthy instances would still be replaced.

Q21.The ALB health check calls /number-customers, which queries RDS. When RDS slowed down, the ASG terminated every web instance. What is the fix?
ASwitch the ASG to EC2 status checks and remove the ALB
BIncrease the ASG's maximum capacity
CAdd a longer cooldown period
DPoint the health check at a lightweight /health endpoint that checks only the instance
✓ Correct: D. Point the health check at a lightweight /health endpoint that checks only the instance

How to think about it: A health check should test the instance itself, simply. It should not depend on downstream systems.

Why the others are wrong:
A) Switch the ASG to EC2 status checks and remove the ALB — This loses application-level health checking and load balancing.
B) Increase the ASG's maximum capacity — More instances would fail the same check.
C) Add a longer cooldown period — A cooldown only delays the cycle. It does not remove the dependency.

Q23.An ECS task must read from one S3 bucket. Other tasks on the same EC2 instance must not get that access. Where should the permission go?
AIn an S3 bucket ACL that allows the cluster
BIn the ECS task IAM role
CAs access keys in environment variables
DIn the EC2 instance profile
✓ Correct: B. In the ECS task IAM role

Q33.A Lambda function is CPU-bound and slow. How do you give it more CPU?
ASet the vCPU count in the function configuration
BRaise the reserved concurrency
CEnable provisioned concurrency
DIncrease the memory setting
✓ Correct: D. Increase the memory setting

How to think about it: CPU is tied to memory: more memory means more vCPU (about 2 vCPUs at 1,769 MB, 6 vCPUs at 10,240 MB).
