CloudFrontFundamental
Q1.What is the main job of Amazon CloudFront?
AA regional load balancer that spreads traffic over targets
BA static anycast IP front door that proxies TCP and UDP
CA CDN that caches content at edge locations near users
DA DNS service that routes users by latency or geography
✓ Correct: C. A CDN that caches content at edge locations near users

How to think about it: CloudFront = CDN: cache content at edge locations close to users.

Why C is correct: CloudFront caches responses at its global points of presence, so users get content from a nearby location instead of the origin.

Why the others are wrong:
A) A regional load balancer that spreads traffic over targets — That is Elastic Load Balancing. CloudFront is a global edge service, and it can use a load balancer as its origin.
B) A static anycast IP front door that proxies TCP and UDP — That is Global Accelerator. It does not cache content; it only carries traffic over the AWS backbone.
D) A DNS service that routes users by latency or geography — That is Route 53. CloudFront is reached by a DNS name, but it does not answer DNS queries for your domain.
CloudFrontFundamental
Q2.What is the role of a CloudFront Regional Edge Cache?
AA larger middle cache that keeps less popular objects longer
BA cache used only for dynamic, uncacheable API responses
CA cache that runs inside your own VPC for private clients
DA replica of your S3 bucket kept in every AWS Region
✓ Correct: A. A larger middle cache that keeps less popular objects longer

How to think about it: Regional Edge Cache = a bigger, longer-lived middle cache between edge locations and the origin.

Why A is correct: Regional edge caches sit between edge locations and the origin. They hold objects longer, which cuts the number of trips to the origin.

Why the others are wrong:
B) A cache used only for dynamic, uncacheable API responses — Dynamic, uncacheable requests skip the regional edge cache and go straight to the origin.
C) A cache that runs inside your own VPC for private clients — CloudFront caches are AWS-run edge sites. They are never deployed into your VPC.
D) A replica of your S3 bucket kept in every AWS Region — That describes S3 Cross-Region Replication. A regional edge cache holds cached copies, not a full bucket.
CloudFrontFundamental
Q3.You want an S3 bucket to be readable only through your CloudFront distribution. What is the current recommended method?
AA custom origin header checked by an S3 bucket policy condition
BOrigin Access Control plus a bucket policy for the distribution
CAn S3 gateway endpoint so CloudFront reaches S3 privately
DTurn on S3 static website hosting and block public access
✓ Correct: B. Origin Access Control plus a bucket policy for the distribution

How to think about it: Private S3 behind CloudFront = Origin Access Control (OAC) + a bucket policy that trusts the distribution.

Why B is correct: OAC signs CloudFront's requests to S3, and the bucket policy allows only that distribution. OAC replaces the older Origin Access Identity (OAI).

Why the others are wrong:
A) A custom origin header checked by an S3 bucket policy condition — Custom headers are the pattern for ALB and custom origins. For S3, OAC is the supported method.
C) An S3 gateway endpoint so CloudFront reaches S3 privately — CloudFront does not run inside your VPC, so a gateway endpoint has no effect on CloudFront's requests.
D) Turn on S3 static website hosting and block public access — A website endpoint is a custom origin that needs public access, and it cannot use OAC.
CloudFrontFundamental
Q4.Where must an ACM certificate be created or imported so that a CloudFront distribution can use it?
AThe same Region as the origin load balancer
BUS East (N. Virginia), us-east-1
CAny Region, as long as it is shared through AWS RAM
DEvery Region that has a CloudFront edge location
✓ Correct: B. US East (N. Virginia), us-east-1

How to think about it: CloudFront certificate = us-east-1 (N. Virginia), always.

Why B is correct: CloudFront is a global service and reads its viewer certificates from ACM in us-east-1 only.

Why the others are wrong:
A) The same Region as the origin load balancer — That rule applies to ALB and NLB certificates. CloudFront ignores certificates held in other Regions.
C) Any Region, as long as it is shared through AWS RAM — ACM certificates are not shared with RAM for CloudFront. The certificate has to be in us-east-1.
D) Every Region that has a CloudFront edge location — Edge locations are not ACM Regions. One certificate in us-east-1 covers the whole distribution.
CloudFrontFundamental
Q5.How do most CloudFront distributions serve HTTPS for a custom domain such as www.example.com without extra cost?
AA dedicated IP address at every edge location
BThe default *.cloudfront.net certificate on the alias
CSNI with a matching certificate
DA self-signed certificate uploaded to the IAM store
✓ Correct: C. SNI with a matching certificate

How to think about it: Custom domain over HTTPS on CloudFront = SNI (dedicated IP is the expensive legacy option).

Why C is correct: SNI lets many certificates share the same edge IPs. It is free and works with all modern clients.

Why the others are wrong:
A) A dedicated IP address at every edge location — Dedicated IPs exist only for very old clients without SNI support, and they cost a lot each month.
B) The default *.cloudfront.net certificate on the alias — The default certificate covers only cloudfront.net names, so browsers would reject www.example.com.
D) A self-signed certificate uploaded to the IAM store — Viewers would not trust a self-signed certificate. CloudFront needs one from a trusted CA.

Q6.Which CloudFront feature sends requests for /images/* to S3 and /api/* to an ALB?
AGeo restriction rules that pick an origin per country
BLambda@Edge on the viewer request to rewrite each host
CAn origin group with a primary and a secondary origin
DCache behaviors with path patterns, one per origin
✓ Correct: D. Cache behaviors with path patterns, one per origin

How to think about it: Different paths to different origins = cache behaviors with path patterns.

Why D is correct: Each cache behavior matches a path pattern and points to its own origin, with its own caching settings.

Why the others are wrong:
A) Geo restriction rules that pick an origin per country — Geo restriction only allows or blocks countries; it never chooses an origin.
B) Lambda@Edge on the viewer request to rewrite each host — This could work, but it is custom code for something cache behaviors already do natively.
C) An origin group with a primary and a secondary origin — Origin groups are for failover between two origins, not for splitting traffic by path.
CloudFrontFundamental
Q7.What does a CloudFront origin group provide?
AFailover to a secondary origin when the primary returns errors
BLoad balancing that splits requests evenly between origins
CA way to cache a single object in two Regions at once
DA shared cache that several distributions can read from
✓ Correct: A. Failover to a secondary origin when the primary returns errors

How to think about it: Origin group = primary + secondary origin = automatic failover.

Why A is correct: If the primary returns a configured error code or times out, CloudFront retries the same request on the secondary origin.

Why the others are wrong:
B) Load balancing that splits requests evenly between origins — Origin groups do not split traffic. The secondary origin is used only when the primary fails.
C) A way to cache a single object in two Regions at once — Caching happens at the edge whatever the origin is. Origin groups exist for availability.
D) A shared cache that several distributions can read from — Each distribution has its own cache. Origin groups are only about choosing an origin.
CloudFrontFundamental
Q8.Which CloudFront feature blocks viewers from specific countries across a whole distribution?
AGeo restriction with an allow list or a block list
BRoute 53 geolocation routing on the alias record
CA security group on the origin that drops foreign IPs
DA cache policy that adds the country header to the key
✓ Correct: A. Geo restriction with an allow list or a block list

How to think about it: Block or allow by country at the CDN = CloudFront geo restriction.

Why A is correct: Geo restriction lets you allow or block countries, using a GeoIP database, for the whole distribution.

Why the others are wrong:
B) Route 53 geolocation routing on the alias record — Geolocation routing changes which answer DNS returns. It does not block anyone at CloudFront.
C) A security group on the origin that drops foreign IPs — Security groups have no country awareness, and CloudFront's edge IPs reach the origin, not viewer IPs.
D) A cache policy that adds the country header to the key — This would cache separately per country, but it still serves every country.
CloudFrontAdvanced
Q9.An ALB origin must accept traffic only from your CloudFront distribution, including traffic from the same edge IPs used by other customers. What is the most reliable control?
AA network ACL on the ALB subnets with the edge IP ranges
BA secret custom header added by CloudFront and checked by ALB rules
CA security group that allows only the CloudFront managed prefix list
DOrigin Access Control attached to the ALB origin
✓ Correct: B. A secret custom header added by CloudFront and checked by ALB rules

How to think about it: ALB only behind your distribution = secret custom origin header checked by the ALB (plus the CloudFront prefix list).

Why B is correct: Only your distribution knows the header value, so the ALB can reject anything without it. Other CloudFront customers share the same edge IPs.

Why the others are wrong:
A) A network ACL on the ALB subnets with the edge IP ranges — NACLs have rule limits and, like the prefix list, cannot tell your distribution apart from others.
C) A security group that allows only the CloudFront managed prefix list — This blocks the open internet, but every CloudFront distribution uses those IPs, including other people's.
D) Origin Access Control attached to the ALB origin — OAC supports S3, Lambda URLs and some media origins. It is not the control for ALB custom origins.
CloudFrontAdvanced
Q10.An application sits on an ALB and EC2 in private subnets. The team wants CloudFront in front of it without giving the ALB a public endpoint. What should they use?
ACloudFront VPC origins pointing at the internal ALB
BAn internet-facing ALB with an IP allow list for CloudFront
CA Global Accelerator in front of a private ALB endpoint
DAn S3 origin with OAC that proxies requests to the ALB
✓ Correct: A. CloudFront VPC origins pointing at the internal ALB

How to think about it: Private ALB, NLB or EC2 behind CloudFront = CloudFront VPC origins.

Why A is correct: VPC origins let CloudFront reach internal ALBs, NLBs and EC2 instances in private subnets, so nothing is exposed to the internet.

Why the others are wrong:
B) An internet-facing ALB with an IP allow list for CloudFront — This works, but it still gives the ALB a public endpoint, which the team wants to avoid.
C) A Global Accelerator in front of a private ALB endpoint — Global Accelerator is a different service with no caching. It does not make the ALB a CloudFront origin.
D) An S3 origin with OAC that proxies requests to the ALB — S3 cannot forward requests to an ALB. OAC only protects S3 and a few other origin types.
CloudFrontAdvanced
Q11.Viewers use HTTPS to CloudFront, and you also want CloudFront-to-origin traffic encrypted to an EC2 web server. What is required at the origin?
AA self-signed certificate with the policy set to match viewer
BAn ACM certificate installed directly on the EC2 instance
CHTTPS-only origin policy and a CA-trusted certificate on the origin
DThe default *.cloudfront.net certificate copied to the origin
✓ Correct: C. HTTPS-only origin policy and a CA-trusted certificate on the origin

How to think about it: End-to-end HTTPS = origin protocol policy HTTPS only + a CA-trusted certificate on the origin.

Why C is correct: CloudFront checks the origin certificate, so it must come from a trusted CA and match the origin domain name. A self-signed one is rejected.

Why the others are wrong:
A) A self-signed certificate with the policy set to match viewer — CloudFront will not accept a self-signed certificate from a custom origin.
B) An ACM certificate installed directly on the EC2 instance — ACM public certificates cannot be exported to EC2. Use a third-party certificate or put an ALB in front.
D) The default *.cloudfront.net certificate copied to the origin — That certificate belongs to AWS and cannot be put on your server.
CloudFrontAdvanced
Q12.The origin needs to know whether each viewer is on a mobile device so it can return a lighter page. How can CloudFront help with no custom code?
AEnable geo restriction so each device type gets its own list
BAdd the full User-Agent header to the cache key everywhere
CForward CloudFront-Is-Mobile-Viewer with an origin request policy
DPut Lambda@Edge on origin response to inspect device IDs
✓ Correct: C. Forward CloudFront-Is-Mobile-Viewer with an origin request policy

How to think about it: Device, country or protocol at the origin = CloudFront-* headers forwarded with an origin request policy.

Why C is correct: CloudFront works out device-type headers from the User-Agent. You can pass them to the origin and add them to the cache key if needed.

Why the others are wrong:
A) Enable geo restriction so each device type gets its own list — Geo restriction works by country only, and it does not tell the origin anything.
B) Add the full User-Agent header to the cache key everywhere — This works but breaks the cache into thousands of variants. The device headers give the same answer much more efficiently.
D) Put Lambda@Edge on origin response to inspect device IDs — The origin response is too late, because the page has already been built. It is also custom code that you don't need.
Edge FunctionsFundamental
Q13.Which statement describes CloudFront Functions?
ACode that runs only on origin request and response events
BNode.js or Python that can call other AWS services
CContainer tasks started at regional edge caches
DLightweight JavaScript on viewer request/response
✓ Correct: D. Lightweight JavaScript on viewer request/response

How to think about it: CloudFront Functions = lightweight JavaScript, viewer request and response only, sub-millisecond, no network calls.

Why D is correct: CloudFront Functions run at edge locations in under a millisecond. They suit header changes, URL rewrites and simple token checks.

Why the others are wrong:
A) Code that runs only on origin request and response events — CloudFront Functions run only on viewer events. Origin events need Lambda@Edge.
B) Node.js or Python that can call other AWS services — That is Lambda@Edge. CloudFront Functions cannot make network calls.
C) Container tasks started at regional edge caches — Neither edge compute option runs containers.
Edge FunctionsFundamental
Q14.Which edge option can run on the origin request and origin response events?
ACloudFront origin request policy
BCloudFront KeyValueStore
CCloudFront Functions
DLambda@Edge
✓ Correct: D. Lambda@Edge

How to think about it: Origin-side events, network access or longer runtime = Lambda@Edge.

Why D is correct: Lambda@Edge supports all four events (viewer and origin, request and response) and can run longer and use the network.

Why the others are wrong:
A) CloudFront origin request policy — An origin request policy picks which headers, cookies and query strings to forward. It runs no code.
B) CloudFront KeyValueStore — KeyValueStore is a data store that CloudFront Functions read from. It does not run code.
C) CloudFront Functions — CloudFront Functions only attach to viewer request and viewer response.
Edge FunctionsAdvanced
Q15.On every request you must rewrite the URL and add a security header, at very high volume and the lowest cost. Which option fits?
AAWS WAF custom responses inserted on every request
BAn ALB listener rule that rewrites the path at the origin
CCloudFront Functions on viewer request and viewer response
DLambda@Edge on origin request and origin response
✓ Correct: C. CloudFront Functions on viewer request and viewer response

How to think about it: Tiny, high-volume header or URL changes = CloudFront Functions, the cheapest and fastest.

Why C is correct: Simple rewrites and headers are the main use case. They cost a fraction of Lambda@Edge and add almost no latency.

Why the others are wrong:
A) AWS WAF custom responses inserted on every request — WAF can insert headers into requests it lets through, but rewriting URLs and adding response headers is the job of edge code.
B) An ALB listener rule that rewrites the path at the origin — ALB rules can redirect, but they run only for cache misses and cannot change every edge response.
D) Lambda@Edge on origin request and origin response — Origin events miss cache hits, so the header would not be added to cached responses. It also costs more.
Edge FunctionsAdvanced
Q16.Before forwarding to the origin, you must look up the user in a DynamoDB table to choose a content version. Which option fits?
ALambda@Edge on the origin request event
BCloudFront Functions on the viewer request event
CA CloudFront origin group with a DynamoDB origin
DA cache policy that includes the user cookie in the key
✓ Correct: A. Lambda@Edge on the origin request event

How to think about it: Needs a network call such as DynamoDB = Lambda@Edge (CloudFront Functions have no network access).

Why A is correct: Lambda@Edge can call other services such as DynamoDB, and the origin request event runs only on cache misses.

Why the others are wrong:
B) CloudFront Functions on the viewer request event — CloudFront Functions cannot make network calls, so they cannot query DynamoDB.
C) A CloudFront origin group with a DynamoDB origin — DynamoDB is not an HTTP origin, and origin groups are only for failover.
D) A cache policy that includes the user cookie in the key — This splits the cache per user, but it cannot look anything up in DynamoDB.
Global AcceleratorFundamental
Q17.What does AWS Global Accelerator give you?
ATwo static anycast IPs over the AWS global backbone
BA dedicated private fiber link from your data center
CA global cache of static objects at hundreds of edges
DA DNS service that returns the closest regional endpoint
✓ Correct: A. Two static anycast IPs over the AWS global backbone

How to think about it: Global Accelerator = 2 static anycast IPs + the AWS backbone + fast regional failover. No caching.

Why A is correct: Users connect at the nearest edge, and the traffic then rides the AWS global network to healthy endpoints.

Why the others are wrong:
B) A dedicated private fiber link from your data center — That is Direct Connect. Global Accelerator serves internet users.
C) A global cache of static objects at hundreds of edges — That is CloudFront. Global Accelerator does not cache content.
D) A DNS service that returns the closest regional endpoint — Route 53 latency routing works through DNS. Global Accelerator uses fixed IPs and anycast routing instead.
Global AcceleratorFundamental
Q18.Which protocols can Global Accelerator handle that CloudFront cannot?
AOnly HTTP and HTTPS, plus WebSocket connections
BAny TCP or UDP traffic, such as gaming or VoIP
CGRE tunnels from on-premises routers into a VPC
DOnly ICMP, for latency testing between Regions
✓ Correct: B. Any TCP or UDP traffic, such as gaming or VoIP

How to think about it: Non-HTTP such as gaming or VoIP over UDP (or raw TCP) = Global Accelerator.

Why B is correct: Global Accelerator works at Layer 4, so it supports non-HTTP workloads such as UDP games and IoT.

Why the others are wrong:
A) Only HTTP and HTTPS, plus WebSocket connections — That describes CloudFront's protocol support, not something extra that Global Accelerator adds.
C) GRE tunnels from on-premises routers into a VPC — GRE is used by Transit Gateway Connect, not by Global Accelerator.
D) Only ICMP, for latency testing between Regions — ICMP is not a Global Accelerator workload.
Global AcceleratorFundamental
Q19.Which of these can be a Global Accelerator endpoint?
AA CloudFront distribution in another account
BAn S3 bucket or a DynamoDB table
CAn ALB, NLB, EC2 instance or Elastic IP
DA Route 53 hosted zone with latency routing
✓ Correct: C. An ALB, NLB, EC2 instance or Elastic IP

How to think about it: GA endpoints = ALB, NLB, EC2, Elastic IP, public or private.

Why C is correct: These four are the supported endpoint types, grouped into endpoint groups per Region.

Why the others are wrong:
A) A CloudFront distribution in another account — CloudFront already has its own global edge network, so it cannot be a GA endpoint.
B) An S3 bucket or a DynamoDB table — Global Accelerator sends traffic to compute and load balancer endpoints, not to storage services.
D) A Route 53 hosted zone with latency routing — A hosted zone answers DNS queries. It does not receive application traffic.
Global AcceleratorAdvanced
Q20.A partner must allow-list your service IPs in their firewall, and the service runs in two Regions behind ALBs. How can you give them a few addresses that never change?
AShare the current ALB node IPs found through a DNS lookup
BAttach Elastic IPs directly to each Application Load Balancer
CFront the ALBs with CloudFront and share the edge IPs
DPut a Global Accelerator in front, then share its two static IPs
✓ Correct: D. Put a Global Accelerator in front, then share its two static IPs

How to think about it: Fixed IPs in front of ALBs that partners can allow-list = Global Accelerator.

Why D is correct: The two anycast IPs stay the same while the ALBs, Regions and their IPs change behind them.

Why the others are wrong:
A) Share the current ALB node IPs found through a DNS lookup — ALB node IPs change as the load balancer scales, so the allow list would break.
B) Attach Elastic IPs directly to each Application Load Balancer — ALBs do not support Elastic IPs; only NLBs do.
C) Front the ALBs with CloudFront and share the edge IPs — CloudFront's edge IP list is very large and changes. It is not a short, fixed list.
Global AcceleratorAdvanced
Q21.An API in two Regions must fail over within seconds if one Region becomes unhealthy, and clients cache DNS for a long time. Which option fails over fastest?
AGlobal Accelerator with per-Region endpoint groups
BRoute 53 failover routing with a 60-second TTL
CAn origin group in CloudFront with two API origins
DCross-zone load balancing on both regional ALBs
✓ Correct: A. Global Accelerator with per-Region endpoint groups

How to think about it: Failover that ignores client DNS caching = Global Accelerator (the IPs stay the same; only the routing changes).

Why A is correct: Health checks move traffic between endpoint groups behind the same IPs, so stale DNS caches don't matter.

Why the others are wrong:
B) Route 53 failover routing with a 60-second TTL — Clients that ignore or extend TTLs keep sending traffic to the failed Region.
C) An origin group in CloudFront with two API origins — This can work for HTTP APIs, but it adds caching semantics and is not a general Layer 4 failover answer.
D) Cross-zone load balancing on both regional ALBs — Cross-zone works inside one Region. It cannot move traffic to another Region.
ALBFundamental
Q22.At which OSI layer does an Application Load Balancer work, and what can it route on?
ALayer 7, routing on path, host, headers and query strings
BLayer 2, bridging Ethernet frames between subnets
CLayer 3, sending all IP packets to virtual appliances
DLayer 4, routing only on IP address and port number
✓ Correct: A. Layer 7, routing on path, host, headers and query strings

How to think about it: ALB = Layer 7: route on path, host, headers, query string and source IP.

Why A is correct: ALB understands HTTP and HTTPS, so listener rules can match request content.

Why the others are wrong:
B) Layer 2, bridging Ethernet frames between subnets — No Elastic Load Balancer works at Layer 2.
C) Layer 3, sending all IP packets to virtual appliances — That is the Gateway Load Balancer, used for firewalls and inspection fleets.
D) Layer 4, routing only on IP address and port number — That is the NLB. It does not look inside HTTP requests.
ALBFundamental
Q23.Which target types can an ALB target group use?
AOnly EC2 instances from an Auto Scaling group
BInstances, private IPs, or a Lambda function
CPublic IP addresses anywhere on the internet
DAn NLB, so traffic can be passed on to Layer 4
✓ Correct: B. Instances, private IPs, or a Lambda function

How to think about it: ALB targets = instances, private IPs, Lambda. (NLB can also target an ALB.)

Why B is correct: ALB target groups can be instances, IPs (including on-premises over DX or VPN), or a single Lambda function.

Why the others are wrong:
A) Only EC2 instances from an Auto Scaling group — Instances are only one of the three ALB target types.
C) Public IP addresses anywhere on the internet — IP targets must be private addresses reachable from the VPC.
D) An NLB, so traffic can be passed on to Layer 4 — It works the other way round: an NLB can use an ALB as its target.
ALBFundamental
Q24.With an ALB in front, how does the backend application learn the real client IP address?
AIt reads the source IP of the packet, which is unchanged
BIt parses a Proxy Protocol v2 header from the ALB
CIt reads the X-Forwarded-For header that the ALB adds
DIt queries VPC Flow Logs for each connection it receives
✓ Correct: C. It reads the X-Forwarded-For header that the ALB adds

How to think about it: Client IP behind an ALB = the X-Forwarded-For header.

Why C is correct: The ALB ends the TCP connection, so the source IP the backend sees is the ALB's. The ALB puts the client IP in X-Forwarded-For.

Why the others are wrong:
A) It reads the source IP of the packet, which is unchanged — That is true for an NLB with instance targets, but not for an ALB.
B) It parses a Proxy Protocol v2 header from the ALB — ALB does not send Proxy Protocol. NLB (v2) and CLB (v1) do.
D) It queries VPC Flow Logs for each connection it receives — Flow logs are delivered after the fact and are not meant for application logic.
ALBFundamental
Q25.What is the difference between the ALB's duration-based and application-based stickiness cookies?
ADuration cookies are for NLB, application cookies for ALB
BBoth are made by the LB and differ only in default lifetime
CThe LB makes the duration cookie; your app sets the other one
DApplication cookies are encrypted; duration ones are not
✓ Correct: C. The LB makes the duration cookie; your app sets the other one

How to think about it: AWSALB = generated by the load balancer and time-based. Application cookie = your app sets it, and the LB tracks it as AWSALBAPP.

Why C is correct: Duration-based stickiness uses the LB-generated AWSALB cookie. Application-based stickiness follows a cookie name that your application sets.

Why the others are wrong:
A) Duration cookies are for NLB, application cookies for ALB — NLB stickiness uses the source IP, not cookies.
B) Both are made by the LB and differ only in default lifetime — Application-based stickiness depends on a cookie that your application sets.
D) Application cookies are encrypted; duration ones are not — The difference is who creates the cookie, not encryption.
ALBFundamental
Q26.On an ALB, cross-zone load balancing is on by default. Can you change it?
ANo, it is always on for ALB and can never be changed
BYes, it can be turned off per target group
COnly on internal ALBs, not on internet-facing ones
DYes, but only by moving the load balancer to one AZ
✓ Correct: B. Yes, it can be turned off per target group

How to think about it: ALB cross-zone: on by default, and it can be turned off per target group.

Why B is correct: AWS now lets you turn off cross-zone at the ALB target group level, for example to keep traffic in one AZ.

Why the others are wrong:
A) No, it is always on for ALB and can never be changed — This was true in the past, but you can now turn it off at the target group level.
C) Only on internal ALBs, not on internet-facing ones — The setting is per target group and has nothing to do with the scheme.
D) Yes, but only by moving the load balancer to one AZ — A single-AZ ALB is not allowed, because an ALB needs at least two AZs.
ALBAdvanced
Q27.One ALB must serve app.example.com and shop.example.org over HTTPS, each with its own certificate. How?
ACreate two ALBs, because each listener holds one certificate
BUse one wildcard certificate for *.example.com on the listener
CPass TCP 443 through and end TLS on the instances
DAdd both certificates to the HTTPS listener and rely on SNI
✓ Correct: D. Add both certificates to the HTTPS listener and rely on SNI

How to think about it: Several HTTPS domains on one listener = SNI with multiple certificates.

Why D is correct: ALB supports several certificates per listener and picks the right one from the SNI hostname the client sends.

Why the others are wrong:
A) Create two ALBs, because each listener holds one certificate — This was a Classic Load Balancer limit. ALB removed it with SNI.
B) Use one wildcard certificate for *.example.com on the listener — A wildcard for example.com does not cover example.org.
C) Pass TCP 443 through and end TLS on the instances — An ALB cannot pass TLS through. It always ends HTTPS itself.
ALBAdvanced
Q28.Each request needs a slow, long-running HTTP connection drained gracefully during deployments. Which ALB setting controls how long in-flight requests can finish?
AThe slow start duration on the target group
BThe health check interval and the unhealthy threshold
CThe load balancer idle timeout, 60 seconds by default
DTarget group deregistration delay (default 300 s)
✓ Correct: D. Target group deregistration delay (default 300 s)

How to think about it: Let in-flight requests finish before removing a target = deregistration delay (connection draining).

Why D is correct: While a target deregisters, the ALB stops sending new requests but lets existing ones finish until the delay runs out.

Why the others are wrong:
A) The slow start duration on the target group — Slow start ramps up traffic to new targets, which is the opposite direction.
B) The health check interval and the unhealthy threshold — These decide when a target counts as unhealthy, not how draining works.
C) The load balancer idle timeout, 60 seconds by default — The idle timeout closes quiet connections. It does not drain targets.
NLBFundamental
Q29.Which load balancer can have one static IP per AZ, including an Elastic IP you choose?
AGateway Load Balancer
BApplication Load Balancer
CClassic Load Balancer
DNetwork Load Balancer
✓ Correct: D. Network Load Balancer

How to think about it: Static or Elastic IP on a load balancer = NLB.

Why D is correct: An NLB has a fixed IP in each enabled AZ, and you can assign your own Elastic IPs to an internet-facing NLB.

Why the others are wrong:
A) Gateway Load Balancer — GWLB is reached through GWLB endpoints in route tables, not through client-facing static IPs.
B) Application Load Balancer — ALB IPs change as it scales. To get static IPs for an ALB, put an NLB or Global Accelerator in front.
C) Classic Load Balancer — CLB is accessed by its DNS name, and its IPs are not fixed.
NLBFundamental
Q30.What is the NLB default for cross-zone load balancing, and what does it cost?
AOn by default and always free, like on an ALB
BNot supported at all on Network Load Balancers
COn by default, but it can be turned off only by AWS Support

Q34.An NLB with IP-type targets (private IPs) shows the NLB's address as the source on the backend, and the app needs client IPs. What is the simplest fix?
