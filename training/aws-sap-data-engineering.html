Kinesis StreamsFundamental
Q1.A new analytics consumer must reprocess the last six months of events from an existing Kinesis data stream. What makes this possible?
ANothing; Kinesis keeps records for at most 7 days
BArchiving each shard to S3 Glacier and replaying from there
CSwitching the stream to on-demand capacity mode
DExtending the stream's retention period, which can go up to 365 days
✓ Correct: D. Extending the stream's retention period, which can go up to 365 days

How to think about it: KDS retention = 24 hours by default, extendable up to 365 days, and consumers can replay.

Why D is correct: Kinesis Data Streams keeps records for 24 hours by default and can be extended to a year, so any consumer can re-read them.

Why the others are wrong:
A) Nothing; Kinesis keeps records for at most 7 days — Seven days was an old ceiling; long-term retention now goes up to 365 days.
B) Archiving each shard to S3 Glacier and replaying from there — Kinesis has no shard archive to Glacier; replay happens from the stream itself.
C) Switching the stream to on-demand capacity mode — Capacity mode controls throughput and billing, not how long records are kept.
Kinesis StreamsFundamental
Q2.In provisioned capacity mode, how much write throughput does a single Kinesis shard accept?
A2 MB per second or 2,000 records per second
B10 MB per second with no record count limit
C1 MB per second or 1,000 records per second
D5 MB per second or 500 records per second
✓ Correct: C. 1 MB per second or 1,000 records per second

How to think about it: Per shard: 1 MB/s or 1,000 records/s in, 2 MB/s out.

Why C is correct: Each shard ingests up to 1 MB/s or 1,000 records/s, whichever limit is hit first.

Why the others are wrong:
A) 2 MB per second or 2,000 records per second — 2 MB/s is the per-shard read limit, not the write limit.
B) 10 MB per second with no record count limit — A shard is far smaller than this and does have a record-rate cap.
D) 5 MB per second or 500 records per second — These figures do not match any Kinesis shard limit.
Kinesis StreamsFundamental
Q3.How does Kinesis Data Streams guarantee the order of records?
ARecords sharing a partition key land in the same shard and stay in order
BBy enabling a FIFO option when the stream is created
CBy setting a message group ID on each record
DAll records in the stream are ordered globally across every shard
✓ Correct: A. Records sharing a partition key land in the same shard and stay in order

How to think about it: Ordering in KDS = same partition key = same shard = in order.

Why A is correct: The partition key is hashed to a shard, and within a shard records keep their sequence.

Why the others are wrong:
B) By enabling a FIFO option when the stream is created — Kinesis streams have no FIFO setting; ordering always comes from the partition key.
C) By setting a message group ID on each record — Message group IDs are how SQS FIFO queues order messages, not Kinesis.
D) All records in the stream are ordered globally across every shard — There is no ordering across different shards, only within one shard.
Kinesis StreamsFundamental
Q4.An application must consume a Kinesis stream with automatic checkpointing and with shards load-balanced across several worker instances. What should the developers use?
AThe Kinesis Producer Library (KPL)
BThe Kinesis Agent
CThe PutRecords API from the AWS SDK
DThe Kinesis Client Library (KCL)
✓ Correct: D. The Kinesis Client Library (KCL)

How to think about it: KPL = Producer (write), KCL = Client/Consumer (read, checkpoint, balance shards).

Why D is correct: KCL handles shard leases, load-balances shards across workers and stores checkpoints (in DynamoDB).

Why the others are wrong:
A) The Kinesis Producer Library (KPL) — KPL optimises writing records (batching, aggregation, retries), not reading them.
B) The Kinesis Agent — The agent is a producer that tails log files and sends them to a stream.
C) The PutRecords API from the AWS SDK — PutRecords writes batches into a stream; it has no consumer checkpointing.
Kinesis StreamsFundamental
Q5.A producer wrote sensitive test records into a Kinesis data stream by mistake. How can they be removed?
AMerge the affected shards so the records are discarded
BCall DeleteRecords with the sequence numbers of the bad records
CPurge the shard from the console as you would an SQS queue
DNot individually; they stay until the retention period expires
✓ Correct: D. Not individually; they stay until the retention period expires

How to think about it: KDS data is immutable: records cannot be deleted, they only expire after retention.

Why D is correct: Kinesis records are immutable, so the only ways to drop them are expiry or deleting the whole stream.

Why the others are wrong:
A) Merge the affected shards so the records are discarded — Merging shards changes capacity; existing data is kept.
B) Call DeleteRecords with the sequence numbers of the bad records — Kinesis has no API to delete single records.
C) Purge the shard from the console as you would an SQS queue — Purging is an SQS feature; Kinesis shards cannot be purged.

Q6.How is data in a Kinesis data stream protected at rest?
AOnly client-side encryption is possible
BServer-side encryption with an AWS KMS key
CSSE-S3 keys, because shards are stored in S3
DA dedicated CloudHSM cluster attached to the stream
✓ Correct: B. Server-side encryption with an AWS KMS key

How to think about it: KDS encryption: KMS server-side at rest, HTTPS in flight.

Why B is correct: Kinesis can encrypt records at rest with an AWS managed or customer managed KMS key.

A) Only client-side encryption is possible — Client-side encryption is optional; Kinesis also offers built-in server-side encryption.
C) SSE-S3 keys, because shards are stored in S3 — SSE-S3 is an S3 bucket feature; Kinesis uses KMS for at-rest encryption.

Kinesis StreamsAdvanced
Q7.An IoT stream has highly unpredictable traffic that can jump tenfold without warning. The team does not want to plan or resize shards. Which choice fits best?
AProvisioned mode with shard splitting done by hand each week
BProvisioned mode sized for today's average traffic
CKinesis Data Streams in on-demand capacity mode
DAn SQS standard queue in place of the stream
✓ Correct: C. Kinesis Data Streams in on-demand capacity mode

How to think about it: Unknown or spiky traffic, no shard management = KDS on-demand mode.

Why C is correct: On-demand mode scales capacity automatically from observed traffic and bills per stream-hour and per GB.

Why the others are wrong:
A) Provisioned mode with shard splitting done by hand each week — Manual resharding is exactly the management work the team wants to avoid.
B) Provisioned mode sized for today's average traffic — Provisioned mode would throttle when traffic spikes past the fixed shard count.
D) An SQS standard queue in place of the stream — SQS scales, but it gives up replay, ordering by key and multiple independent readers.
Kinesis StreamsAdvanced
Q8.Producers send 3,000 records per second, each about 1 KB, into a provisioned Kinesis stream. What is the minimum number of shards?
A2 shards
B3 shards
C1 shard
D6 shards
✓ Correct: B. 3 shards

How to think about it: Shards in = max(MB/s / 1, records/s / 1,000). 3 MB/s and 3,000 rec/s = 3 shards.

Why B is correct: 3,000 records of 1 KB is about 3 MB/s and 3,000 records/s, and each shard takes 1 MB/s and 1,000 records/s.

Why the others are wrong:
A) 2 shards — Two shards would suit the 2 MB/s read limit, but writes are capped at 1 MB/s per shard.
C) 1 shard — One shard takes only 1 MB/s and 1,000 records/s, a third of what is needed.
D) 6 shards — Six shards would work but double the cost; three is the minimum.
Kinesis StreamsAdvanced
Q9.Five separate applications read the same Kinesis stream, and each is being throttled on reads. Every application needs its own full read throughput with the lowest latency. What should you enable?
AA longer retention period
BKPL record aggregation
CA larger GetRecords batch size
DEnhanced fan-out for each consumer
✓ Correct: D. Enhanced fan-out for each consumer

How to think about it: Many consumers on one stream = enhanced fan-out (2 MB/s per shard per consumer, push, ~70 ms).

Why D is correct: Each registered consumer gets its own 2 MB/s per shard pushed over HTTP/2, so they no longer share the read limit.

Why the others are wrong:
A) A longer retention period — Retention controls how long data is kept, not how fast it can be read.
B) KPL record aggregation — Aggregation improves producer efficiency; it does not add read throughput.
C) A larger GetRecords batch size — Bigger batches still share the same 2 MB/s per shard among all five consumers.
Kinesis StreamsAdvanced
Q10.Several independent teams must each read the same ordered event stream at their own pace and be able to replay the last three days. Which service fits?
AAn SNS standard topic
BAn SQS standard queue
CKinesis Data Streams
DAn SQS FIFO queue
✓ Correct: C. Kinesis Data Streams

How to think about it: Multiple readers + ordering + replay = Kinesis Data Streams (or MSK), not SQS or SNS.

Why C is correct: KDS keeps records for the retention period, orders them per shard, and lets many consumers read the same data independently.

Why the others are wrong:
A) An SNS standard topic — SNS pushes and forgets; there is no retention or replay.
B) An SQS standard queue — SQS deletes a message once it is consumed, has no ordering and cannot replay.
D) An SQS FIFO queue — FIFO keeps order but still removes each message after a consumer deletes it.
Data FirehoseFundamental
Q11.Clickstream events must land in Amazon S3 in near real time with automatic scaling and no consumer code to write or run. What should you use?
AAmazon MSK with a custom Kafka consumer
BKinesis Data Streams with a KCL app on EC2
CAmazon Data Firehose
DAn SQS queue drained by a cron job
✓ Correct: C. Amazon Data Firehose

How to think about it: Load streaming data into S3, Redshift, OpenSearch, Splunk or HTTP with no code = Amazon Data Firehose.

Why C is correct: Firehose is fully managed and serverless: it buffers incoming records and delivers them to destinations such as S3.

Why the others are wrong:
A) Amazon MSK with a custom Kafka consumer — MSK needs consumer applications and broker sizing, which is not code-free.
B) Kinesis Data Streams with a KCL app on EC2 — This works, but you would write and operate the consumer code yourself.
D) An SQS queue drained by a cron job — Polling SQS on a schedule is custom code and not near real time.
Data FirehoseFundamental
Q12.How does Amazon Data Firehose load data into a provisioned Amazon Redshift cluster?
AIt registers the data as a Redshift Spectrum external table
BIt stages files in S3, then runs a Redshift COPY
CIt triggers an AWS Glue job that performs the load
DIt sends one INSERT statement per record over JDBC
✓ Correct: B. It stages files in S3, then runs a Redshift COPY

How to think about it: Firehose to Redshift = S3 first, then COPY.

Why B is correct: Firehose stages batches in S3 and issues COPY, which is the efficient bulk-load path into Redshift.

Why the others are wrong:
A) It registers the data as a Redshift Spectrum external table — Spectrum queries data left in S3; Firehose loads into cluster tables.
C) It triggers an AWS Glue job that performs the load — Firehose handles the load itself without a Glue job.
D) It sends one INSERT statement per record over JDBC — Row-by-row inserts would be very slow in Redshift; Firehose does not do this.
Data FirehoseFundamental
Q13.Incoming records arrive as CSV and must be reshaped into JSON before Firehose delivers them. What is the simplest approach?
AUse the Kinesis Agent to rewrite the files on S3
BEnable Firehose data transformation with a Lambda function
CConfigure an S3 Lifecycle rule to convert the objects
DInsert a Glue crawler between the producer and Firehose
✓ Correct: B. Enable Firehose data transformation with a Lambda function

How to think about it: Firehose custom transformation = Lambda (blueprints available).

Why B is correct: Firehose invokes Lambda on each buffered batch, and the function returns the reshaped records.

Why the others are wrong:
A) Use the Kinesis Agent to rewrite the files on S3 — The agent ships log files; it does not convert data after delivery.
C) Configure an S3 Lifecycle rule to convert the objects — Lifecycle rules move or expire objects; they never change their content.
D) Insert a Glue crawler between the producer and Firehose — Crawlers discover schemas; they do not transform records in flight.
Data FirehoseFundamental
Q14.Some records fail Lambda transformation or delivery to the destination. The team must keep them for later analysis. What should they configure?
AA longer retention period on the Firehose stream
BAn S3 backup location for failed (or all) records
CA dead-letter queue on the Firehose stream
DEnhanced fan-out on the delivery stream
✓ Correct: B. An S3 backup location for failed (or all) records

How to think about it: Firehose failures (or all source data) go to an S3 backup bucket.

Why B is correct: Firehose writes records that fail transformation or delivery to an S3 bucket, and it can back up all source data too.

Why the others are wrong:
A) A longer retention period on the Firehose stream — Firehose does not store data for replay, so there is no retention to extend.
C) A dead-letter queue on the Firehose stream — Firehose has no SQS dead-letter queue; it uses S3 for failures.
D) Enhanced fan-out on the delivery stream — Enhanced fan-out is a Kinesis Data Streams consumer feature.
Data FirehoseFundamental
Q15.A Firehose stream receives very little traffic. Which buffering rule will usually cause it to flush data to the destination?
AThe shard count of the stream is exceeded
BThe retention period expires
CThe buffer size threshold is reached
DThe buffer interval (time) is reached
✓ Correct: D. The buffer interval (time) is reached

How to think about it: Firehose buffer: low traffic = time limit hits, high traffic = size limit hits.

Why D is correct: With little data, the size threshold is rarely met, so the time limit triggers delivery.

Why the others are wrong:
A) The shard count of the stream is exceeded — Firehose has no shards to manage.
B) The retention period expires — Firehose has no retention period; it only buffers before delivery.
C) The buffer size threshold is reached — Size is usually hit first when throughput is high, not low.

AEnable Firehose record format conversion with a Glue schema

DWrite a Lambda transformation that builds Parquet files
