Q1.What is the maximum size of a single item in a DynamoDB table?
A64 KB
B4 MB
C16 MB
D400 KB
✓ Correct: D. 400 KB

How to think about it: DynamoDB item limit = 400 KB. Bigger payloads go to S3 with a pointer in the item.

Why D is correct: An item, including attribute names and values, can be at most 400 KB; larger data belongs in S3.

Why the others are wrong:
A) 64 KB — 64 KB is far below the real limit and is not a DynamoDB item boundary.
B) 4 MB — 4 MB is ten times the real limit; DynamoDB would reject such an item.
C) 16 MB — 16 MB is the MongoDB/DocumentDB document limit, not DynamoDB's.

Q2.When must you choose the primary key of a DynamoDB table?
AAny time, with an UpdateTable call
BWhen the first global secondary index is added
CAt table creation, and it cannot be changed later
DWhen the first item is written to the table
✓ Correct: C. At table creation, and it cannot be changed later

How to think about it: Primary key = fixed at table creation. Changing it means a new table and a data copy.

Why C is correct: The key schema is part of the table definition; a different key requires creating a new table.

Why the others are wrong:
A) Any time, with an UpdateTable call — UpdateTable changes capacity, indexes and streams, but never the base table's key schema.
B) When the first global secondary index is added — A GSI defines its own key; it does not set the base table's primary key.
D) When the first item is written to the table — The key must already exist before any item can be written.

Q3.A users table uses only a partition key. Which attribute makes the best partition key?
Auser_id, unique for every user
Baccount_status, such as active or closed
Csignup_date, the day the user joined
Dcountry, shared by many users
✓ Correct: A. user_id, unique for every user

How to think about it: Partition key alone = unique and high-cardinality (e.g. user_id), so data spreads evenly.

Why A is correct: A unique, diverse value spreads items across partitions and identifies each item on its own.

Why the others are wrong:
B) account_status, such as active or closed — Only a handful of values exist, which concentrates traffic on a few partitions.
C) signup_date, the day the user joined — Many users share a date, so it is neither unique nor evenly distributed.
D) country, shared by many users — Country is low-cardinality and not unique, so items collide and partitions get hot.

Q4.A game table must store many results per player and return one player's games in order of play time. Which primary key design fits?
APartition key user_id with no sort key
BPartition key game_timestamp with no sort key
CPartition key result with sort key user_id
DPartition key user_id with sort key game_timestamp
✓ Correct: D. Partition key user_id with sort key game_timestamp

How to think about it: One-to-many inside a key = partition key + sort key; the pair must be unique, and a timestamp is a classic sort key.

Why D is correct: Items are grouped by player and ordered by time, and the pair is unique for each game.

Why the others are wrong:
A) Partition key user_id with no sort key — Without a sort key, each player could hold only one item.
B) Partition key game_timestamp with no sort key — This scatters a player's games across partitions, so you cannot query one player efficiently.
C) Partition key result with sort key user_id — Result has only a few values (win or lose), giving hot partitions and the wrong grouping.

Q5.You need a second sort order on a DynamoDB table while keeping the same partition key, and the table is still being designed. Which index fits?
AA DynamoDB Streams view
BA global secondary index (GSI)
CA sparse attribute with a TTL value
DA local secondary index (LSI)
✓ Correct: D. A local secondary index (LSI)

How to think about it: Same partition key, different sort key, defined at creation = LSI.

Why D is correct: An LSI keeps the table's partition key, adds an alternative sort key, and must be declared when the table is created.

Why the others are wrong:
A) A DynamoDB Streams view — Streams record item changes; they do not provide an alternative query order.
B) A global secondary index (GSI) — A GSI can use a whole new partition key; it is not limited to the base partition key.
C) A sparse attribute with a TTL value — TTL deletes expired items; it does not add a way to sort or query them.

DDynamoDB Accelerator in front of the table

Q7.Traffic to a new DynamoDB table is spiky and impossible to forecast, and the team wants no capacity planning at all. Which capacity mode fits?
AProvisioned mode with reserved capacity
BProvisioned mode with fixed RCUs and WCUs
COn-demand capacity mode
DStandard-Infrequent Access table class
✓ Correct: C. On-demand capacity mode

How to think about it: Unknown or spiky traffic = on-demand; steady, forecastable traffic = provisioned + auto scaling.

Why C is correct: On-demand bills per request and absorbs sudden changes with no RCU or WCU planning.

Why the others are wrong:
A) Provisioned mode with reserved capacity — Reserved capacity is a discount for steady, predictable throughput.
B) Provisioned mode with fixed RCUs and WCUs — Fixed capacity must be forecast and will throttle when spikes exceed it.
D) Standard-Infrequent Access table class — Table class changes storage pricing; it does not decide how throughput is handled.

Q8.A table has a steady, well-understood daily load and cost is the main concern. Which capacity setup is usually cheapest?
AA DAX cluster with no table capacity set
BProvisioned capacity with auto scaling
COn-demand capacity mode
DGlobal tables in two Regions
✓ Correct: B. Provisioned capacity with auto scaling

How to think about it: Predictable load + cost focus = provisioned capacity with auto scaling.

Why B is correct: Provisioned capacity costs less per request than on-demand when usage is steady and forecastable, and auto scaling follows the daily curve.

Why the others are wrong:
A) A DAX cluster with no table capacity set — DAX is a cache; the table still needs a capacity mode.
C) On-demand capacity mode — On-demand is simple but has a higher unit price for steady traffic.
D) Global tables in two Regions — Global tables add replicas and cost; they do not reduce spend on a single-Region load.

Q9.Right after writing an item, an application must read it back and always see the latest value. What should the read use?
AAn eventually consistent read
BA read from a global table replica in another Region
CA read through DynamoDB Accelerator
DA strongly consistent read
✓ Correct: D. A strongly consistent read

How to think about it: Must see the last write = strongly consistent read (ConsistentRead = true). Default reads are eventually consistent.

Why D is correct: Setting ConsistentRead returns the most recent committed value, at twice the read capacity cost.

Why the others are wrong:
A) An eventually consistent read — This is the default and may briefly return stale data after a write.
B) A read from a global table replica in another Region — Cross-Region replication is asynchronous, so the replica can lag.
C) A read through DynamoDB Accelerator — DAX serves cached items and is eventually consistent by design.

Q10.A large DynamoDB table holds years of data that is rarely read, and storage is now most of the bill. Which change helps most?
AAdd a DAX cluster in front of the table
BSwitch the table to on-demand capacity mode
CUse the Standard-IA table class
DEnable DynamoDB Streams on the table
✓ Correct: C. Use the Standard-IA table class

How to think about it: Storage-heavy, rarely accessed table = Standard-IA table class.

Why C is correct: Standard-IA lowers storage price for tables where storage, not throughput, dominates cost.

Why the others are wrong:
A) Add a DAX cluster in front of the table — A cache adds cost and does nothing for stored data volume.
B) Switch the table to on-demand capacity mode — On-demand changes how requests are billed, not what storage costs.
D) Enable DynamoDB Streams on the table — Streams capture changes and do not change storage pricing.

Q11.An order service must deduct stock in an Inventory table and create a row in an Orders table so that either both writes succeed or neither does. What should it use?
ATwo PutItem calls with a conditional expression
BBatchWriteItem covering both tables
CTransactWriteItems covering both tables
DA stream-triggered Lambda that writes the second table
✓ Correct: C. TransactWriteItems covering both tables

How to think about it: All-or-nothing across items or tables = DynamoDB transactions (TransactWriteItems).

Why C is correct: DynamoDB transactions give ACID, all-or-nothing writes across multiple items and tables.

Why the others are wrong:
A) Two PutItem calls with a conditional expression — A condition protects one item, but the two writes can still end up half-done.
B) BatchWriteItem covering both tables — Batch writes are not atomic; some items can succeed while others fail.
D) A stream-triggered Lambda that writes the second table — This is eventually consistent and leaves a window where only one table changed.

Q12.Millions of objects land in S3, and customers need an API to find their objects by upload date range and to total their storage. S3 listing is too slow. What is the usual design?
ATurn on S3 Versioning and read the version history
BS3 events invoke Lambda to index object metadata in DynamoDB
CUse S3 Lifecycle rules to group objects by date
DEnable S3 Transfer Acceleration and keep listing the bucket
✓ Correct: B. S3 events invoke Lambda to index object metadata in DynamoDB

How to think about it: S3 is not searchable by metadata, so index object metadata in DynamoDB using an S3 event and Lambda.

Why B is correct: Each upload's key, size, owner and date go into a table keyed for the access patterns, giving fast queries and totals.

Why the others are wrong:
A) Turn on S3 Versioning and read the version history — Versioning keeps old copies; it does not give a queryable index by date or owner.
C) Use S3 Lifecycle rules to group objects by date — Lifecycle rules move or expire objects; they cannot answer queries.
D) Enable S3 Transfer Acceleration and keep listing the bucket — Transfer Acceleration speeds uploads; it does not make listing or filtering faster.

Q13.Session records in DynamoDB should disappear automatically a day after they are created, without paying for delete writes. What should you use?
AThe Standard-IA table class
BTime to Live (TTL) on an epoch-time attribute
CPoint-in-time recovery with a short window
DA nightly Lambda that scans and deletes old items
✓ Correct: B. Time to Live (TTL) on an epoch-time attribute

How to think about it: Auto-expire items = TTL attribute holding an epoch timestamp.

C) Point-in-time recovery with a short window — PITR keeps restore points; it does not delete current data.
D) A nightly Lambda that scans and deletes old items — This works but costs read and write capacity and is custom code TTL already replaces.

DCloudTrail data events for DynamoDB
✓ Correct: B. DynamoDB Streams

Q19.One very popular product item is read thousands of times per second and its partition keeps throttling, while the rest of the table is quiet. What is the simplest fix?
AEnable DynamoDB Streams on the table

CPut DAX in front of the table so repeat reads come from cache
DSwitch the table to the Standard-IA table class
✓ Correct: C. Put DAX in front of the table so repeat reads come from cache
