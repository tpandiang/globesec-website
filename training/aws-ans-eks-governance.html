EKS ClusterFundamental
Q1.In Amazon EKS, where do the control plane and the worker nodes run?
ABoth run in an AWS-managed VPC that you then peer with
BBoth the control plane and the nodes run in your own VPC
CControl plane in an AWS-managed VPC; nodes in your VPC
DControl plane in your VPC; nodes in an AWS-managed VPC
✓ Correct: C. Control plane in an AWS-managed VPC; nodes in your VPC

How to think about it: Control plane = AWS-managed VPC; data plane (nodes) = your VPC.

Why C is correct: AWS runs the API server and etcd for you, while nodes and pods live in your subnets.

Why the others are wrong:
A) Both run in an AWS-managed VPC that you then peer with — Worker nodes run in your VPC, and no peering is required.
B) Both the control plane and the nodes run in your own VPC — You never see or manage the control plane instances in your account.
D) Control plane in your VPC; nodes in an AWS-managed VPC — This reverses the model: AWS manages the control plane, you own the node subnets.
EKS ClusterFundamental
Q2.How does the EKS control plane talk to worker nodes in your VPC (for example for kubectl exec or logs)?
AThrough a VPC peering connection EKS creates for you
BThrough the internet gateway using the node public IPs
CThrough EKS-owned ENIs placed in your cluster subnets
DThrough a Transit Gateway attachment in your account
✓ Correct: C. Through EKS-owned ENIs placed in your cluster subnets

How to think about it: Control plane → nodes = EKS-owned cross-account ENIs placed in your subnets.

Why C is correct: EKS creates 2-4 ENIs in the subnets you choose, giving the control plane a private path into the VPC.

Why the others are wrong:
A) Through a VPC peering connection EKS creates for you — EKS does not peer VPCs; it uses cross-account ENIs.
B) Through the internet gateway using the node public IPs — Nodes can be fully private; the control plane does not need their public IPs.
D) Through a Transit Gateway attachment in your account — No TGW is involved in control plane to node communication.

ADisabled until you create an interface endpoint

CPublic access enabled and private access disabled
DPrivate access only, reachable from inside the VPC
✓ Correct: C. Public access enabled and private access disabled

Why the others are wrong:
A) Disabled until you create an interface endpoint — The endpoint works immediately after cluster creation.
B) Reachable only through AWS Systems Manager Session Manager — Session Manager is not how the Kubernetes API is exposed.
D) Private access only, reachable from inside the VPC — Private-only is a configuration you choose; it is not the default.

Q4.An EKS cluster has public endpoint access disabled and private access enabled. A developer on-premises over Direct Connect cannot resolve the API endpoint name. What is the usual fix?
ATurn on the DNS hostnames attribute for the on-prem network
BCreate an S3 gateway endpoint for the EKS API in the VPC
CAdd the control plane CIDR to the Direct Connect public VIF
DForward the name to a Route 53 Resolver inbound endpoint
✓ Correct: D. Forward the name to a Route 53 Resolver inbound endpoint

How to think about it: Private EKS endpoint from on-prem = Route 53 Resolver inbound endpoint (or conditional forwarding) + routing.

Why D is correct: The private endpoint name resolves to the EKS ENI IPs only inside the VPC, so on-premises DNS must forward to the VPC resolver.

Why the others are wrong:
A) Turn on the DNS hostnames attribute for the on-prem network — DNS hostnames is a VPC attribute, not something set on the on-premises network.
B) Create an S3 gateway endpoint for the EKS API in the VPC — Gateway endpoints only support S3 and DynamoDB.
C) Add the control plane CIDR to the Direct Connect public VIF — A public VIF carries AWS public prefixes; the private endpoint uses private ENI IPs.

Pod NetworkingFundamental
Q6.With the Amazon VPC CNI plugin, where does each pod's IP address come from?
AThe node's primary IP, shared by all pods through port mapping
BA secondary private IP on an ENI attached to the node
CAn Elastic IP allocated to each pod by the CNI
DAn overlay network range that is invisible to the VPC
✓ Correct: B. A secondary private IP on an ENI attached to the node

How to think about it: VPC CNI = pods get real VPC IPs (secondary IPs on node ENIs).

Why B is correct: The CNI attaches ENIs to the node and hands out their secondary IPs to pods, so pods are first-class VPC addresses.

Why the others are wrong:
A) The node's primary IP, shared by all pods through port mapping — Each pod gets its own IP; it does not share the node IP.
C) An Elastic IP allocated to each pod by the CNI — Pods use private VPC IPs; EIPs are not allocated per pod.
D) An overlay network range that is invisible to the VPC — That is how many overlay CNIs work, but the VPC CNI uses native VPC IPs.

Q7.What mainly limits the maximum number of pods on an EKS EC2 node with default VPC CNI settings?
AThe number of security groups attached to the node
BThe size and type of the node's root EBS volume
CThe instance type's ENI count and IPs per ENI
DThe size of the cluster's Kubernetes service CIDR
✓ Correct: C. The instance type's ENI count and IPs per ENI

How to think about it: Max pods = ENIs × (IPs per ENI − 1) + 2 → set by instance type.

Why C is correct: Each ENI's secondary IPs go to pods, so instance type ENI limits cap the pod count.

Why the others are wrong:
A) The number of security groups attached to the node — Security group count does not decide how many pod IPs a node has.
B) The size and type of the node's root EBS volume — Storage size does not limit pod IP allocation.
D) The size of the cluster's Kubernetes service CIDR — The service CIDR is used for ClusterIP addresses, not pod IPs.

Q8.What does VPC CNI prefix delegation do?
ALets pods borrow unused IP addresses from a peered VPC
BDelegates the pod CIDR to an on-premises DHCP server
CMoves pod addresses into the node's public IPv4 pool
DAssigns /28 prefixes to ENI slots, raising pod density
✓ Correct: D. Assigns /28 prefixes to ENI slots, raising pod density

How to think about it: Prefix delegation = assign /28 (IPv4) or /80 (IPv6) prefixes to ENI slots → many more pods.

Why D is correct: Each slot carries 16 addresses, so Nitro nodes can run far more pods.

Why the others are wrong:
A) Lets pods borrow unused IP addresses from a peered VPC — Pods cannot use another VPC's address space.
B) Delegates the pod CIDR to an on-premises DHCP server — Pod IPs still come from VPC subnets, not on-premises DHCP.
C) Moves pod addresses into the node's public IPv4 pool — Prefix delegation works with private VPC address space.

Pod NetworkingFundamental
Q10.A pod with an IPv4 address in a private subnet calls an internet API. With default SNAT settings, what source IP leaves the node?
AThe pod's own secondary IP all the way to the internet
BThe ClusterIP of the service the pod belongs to
CThe primary private IP of the node's primary ENI
DThe private IP of an EKS control plane ENI
✓ Correct: C. The primary private IP of the node's primary ENI

How to think about it: Default SNAT: traffic leaving the VPC CIDR uses the node's primary ENI IP.

Why C is correct: The VPC CNI translates pod IPs to the node's primary IP for destinations outside the VPC CIDR.

Why the others are wrong:
A) The pod's own secondary IP all the way to the internet — Private IPs are never routable on the internet; a NAT step is always needed.
B) The ClusterIP of the service the pod belongs to — ClusterIPs are virtual and only valid inside the cluster.
D) The private IP of an EKS control plane ENI — Control plane ENIs are not used for pod egress.

Q11.Pods in a private subnet must reach the internet through a NAT gateway, and on-premises firewalls must see the real pod IPs. Which CNI setting should you change?
ASet externalTrafficPolicy=Local on every service
BSet AWS_VPC_K8S_CNI_EXTERNALSNAT=true on aws-node
CAdd an IPv6 CIDR to the VPC and keep the cluster IPv4
DSet ENABLE_POD_ENI=true on the aws-node DaemonSet
✓ Correct: B. Set AWS_VPC_K8S_CNI_EXTERNALSNAT=true on aws-node

How to think about it: Use a NAT gateway / keep pod IPs = AWS_VPC_K8S_CNI_EXTERNALSNAT=true.

Why B is correct: This turns off node SNAT so pod IPs stay visible and an external NAT gateway does the translation.

Why the others are wrong:
A) Set externalTrafficPolicy=Local on every service — That affects inbound load balancer traffic, not pod egress.
C) Add an IPv6 CIDR to the VPC and keep the cluster IPv4 — IPv6 on the VPC does not change IPv4 pod SNAT for an IPv4 cluster.
D) Set ENABLE_POD_ENI=true on the aws-node DaemonSet — That enables security groups for pods, not SNAT behaviour.

Q12.An EKS cluster is running out of IPs in its small /24 node subnets. The team wants more pod IPs without re-IPing the nodes. Which approach fits?
AResize the existing node subnets from /24 to /20 in place
BChange the Kubernetes service CIDR to a larger range
CAdd a 100.64.0.0/10 secondary CIDR and CNI custom networking
DSwitch pods to the node's public IP to save private IPs
✓ Correct: C. Add a 100.64.0.0/10 secondary CIDR and CNI custom networking

How to think about it: Pod IP exhaustion = secondary CIDR (100.64.0.0/10 range) + CNI custom networking.

Why C is correct: Custom networking places pod ENIs in subnets from the secondary CIDR, keeping nodes on their original subnets.

Why the others are wrong:
A) Resize the existing node subnets from /24 to /20 in place — A subnet's CIDR cannot be changed after it is created.
B) Change the Kubernetes service CIDR to a larger range — The service CIDR is for ClusterIPs, not pod IPs.
D) Switch pods to the node's public IP to save private IPs — Pods cannot share public IPs in this way, and it wouldn't add private addresses.

Q13.In an IPv6 EKS cluster, how are pod addresses handled when talking to the internet?
APods use globally unique IPv6 addresses with no NAT
BPods run dual-stack with both IPv4 and IPv6 pod IPs
CPods share one IPv6 address per node through port mapping
DPods are translated to the node's IPv4 address by default
✓ Correct: A. Pods use globally unique IPv6 addresses with no NAT

How to think about it: IPv6 pods = no NAT; use an egress-only IGW for outbound-only.

Why A is correct: IPv6 addresses are not translated; an egress-only internet gateway can allow outbound-only access.

Why the others are wrong:
B) Pods run dual-stack with both IPv4 and IPv6 pod IPs — EKS pods are either IPv4 or IPv6, not dual-stack.
C) Pods share one IPv6 address per node through port mapping — Each pod gets its own IPv6 address from the node's /80 prefix.
D) Pods are translated to the node's IPv4 address by default — SNAT to the node IP is IPv4 behaviour.
Pod SecurityFundamental
Q14.By default with the VPC CNI, which security group applies to a pod?
ANone; pod traffic bypasses security groups entirely
BA unique security group that EKS creates for every pod
COnly the EKS cluster security group, on every pod
DThe SG of the node ENI that supplies the pod's IP
✓ Correct: D. The SG of the node ENI that supplies the pod's IP

How to think about it: Default: pods inherit the SG of the node ENI their IP comes from.

Why D is correct: All pods on the same ENI share that ENI's security groups.

Why the others are wrong:
A) None; pod traffic bypasses security groups entirely — Pod traffic is still filtered by the ENI's security groups.
B) A unique security group that EKS creates for every pod — Per-pod security groups require the separate security groups for pods feature.
C) Only the EKS cluster security group, on every pod — The cluster SG is attached to control plane ENIs and managed nodes; pods use their ENI's SGs.

ACustom networking with a 100.64 secondary CIDR

✓ Correct: B. Security groups for pods (trunk/branch ENIs)

✓ Correct: A. Plans and tracks IP space across accounts and Regions

Q25.In IPAM, what is a scope?
AA single CIDR block allocated to one specific VPC
BA list of accounts that are allowed to create VPCs
CA CloudWatch alarm that watches pool utilization
DA top-level container for private or public IP space
✓ Correct: D. A top-level container for private or public IP space

How to think about it: Scope = top-level container, public or private address space.
