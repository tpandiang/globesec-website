IAM PoliciesFundamental
Q1.An identity-based policy allows s3:*, but a second policy attached to the same user denies s3:DeleteObject. What happens when the user tries to delete an object?
AThe delete succeeds because the broader Allow is evaluated last
BThe delete succeeds because Allow and Deny cancel each other out
CThe result depends on which policy was attached most recently
DThe delete is denied because an explicit Deny overrides any Allow
✓ Correct: D. The delete is denied because an explicit Deny overrides any Allow

How to think about it: Explicit Deny always wins over any Allow.

Why D is correct: IAM evaluation checks for an explicit Deny first; if one matches, no Allow anywhere can override it.

Why the others are wrong:
A) The delete succeeds because the broader Allow is evaluated last — Order of attachment or evaluation does not matter; a matching Deny is final.
B) The delete succeeds because Allow and Deny cancel each other out — There is no cancelling out; a single explicit Deny blocks the request.
C) The result depends on which policy was attached most recently — IAM has no recency rule; every applicable policy is evaluated together.

Q2.If no policy mentions an action at all, what is the result when a user calls it?
AIt is allowed because nothing denies it
BIt is allowed if the user has MFA enabled
CIt is implicitly denied
DIt is allowed only for read-only actions
✓ Correct: C. It is implicitly denied

How to think about it: Nothing says yes = implicit deny.

Why C is correct: IAM denies everything by default; a request needs an explicit Allow and no explicit Deny to succeed.

Why the others are wrong:
A) It is allowed because nothing denies it — IAM is default-deny, so silence never grants access.
B) It is allowed if the user has MFA enabled — MFA status alone grants nothing; it can only be checked in a condition.
D) It is allowed only for read-only actions — There is no special default for read actions; they also need an Allow.

CA Deny statement scoped with a Condition
DAn Allow statement that uses NotResource
✓ Correct: A. An Allow statement that uses NotAction

Why A is correct: NotAction with Allow grants every action except those listed, so IAM and Organizations simply are not granted.

C) A Deny statement scoped with a Condition — A Deny would block those actions even if another policy allowed them, which PowerUserAccess avoids.

Q6.What does an IAM permissions boundary do?
AIt limits every account in an organizational unit
BIt caps the permissions a user or role can ever have
CIt grants permissions to every member of an IAM group
DIt lists which external accounts may assume a role
✓ Correct: B. It caps the permissions a user or role can ever have

How to think about it: Boundary = maximum permissions ceiling; it never grants anything by itself.

Why B is correct: Effective permissions are the overlap of the boundary and the identity policies; the boundary alone grants nothing.

Why the others are wrong:
A) It limits every account in an organizational unit — Limiting accounts across an OU is the job of a service control policy.
C) It grants permissions to every member of an IAM group — Boundaries cannot be attached to groups and they do not grant access.
D) It lists which external accounts may assume a role — That is the role's trust policy, not a boundary.

Q11.A role's sessions were exposed. You must cut off every session already issued for that role without deleting the role. What do you do?
ARotate the role's access keys
BDetach all permission policies from the role
CRevoke active sessions, denying tokens issued before now
DLower the role's maximum session duration to 15 minutes
✓ Correct: C. Revoke active sessions, denying tokens issued before now

How to think about it: Kill issued sessions = revoke active sessions (deny on aws:TokenIssueTime).

Why C is correct: The AWSRevokeOlderSessions inline policy denies all requests whose token was issued before the revoke time.

Why the others are wrong:
A) Rotate the role's access keys — Roles have no long-term access keys; their credentials are temporary.
B) Detach all permission policies from the role — This blocks old and new sessions alike, and the role becomes unusable.
D) Lower the role's maximum session duration to 15 minutes — This affects future sessions only; existing tokens stay valid until they expire.

Q12.What is the key difference between assuming a cross-account role and using a resource-based policy to grant access?
AAssuming a role keeps your permissions and adds the role's
BA role swaps your permissions for the role's; a resource policy keeps yours
CResource policies require the caller to have MFA
DResource policies work only within one account; roles work across accounts
✓ Correct: B. A role swaps your permissions for the role's; a resource policy keeps yours

How to think about it: Assume a role = give up your own permissions. Resource policy = keep them.

Why B is correct: With a resource policy you act as yourself, so you can read in one account and write in the other in the same session.

Why the others are wrong:
A) Assuming a role keeps your permissions and adds the role's — Assuming a role replaces your permissions for that session; they are not merged.
C) Resource policies require the caller to have MFA — MFA is optional and can be required by condition in either approach.
D) Resource policies work only within one account; roles work across accounts — Resource policies such as bucket policies are commonly used to grant other accounts access.

Q13.A user in Account A must scan a DynamoDB table in Account A and write the output into an S3 bucket in Account B in one process. What is the simplest design?

DHave the user assume a role in Account B and then read DynamoDB
✓ Correct: B. Add an S3 bucket policy in Account B that allows the Account A user to write
