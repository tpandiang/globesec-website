TGW BasicsFundamental
Q1.What is an AWS Transit Gateway?
AA managed regional hub router for many VPCs and on-prem networks
BA global edge network that speeds up TCP and UDP traffic to apps
CA load balancer that sends traffic to firewall appliances
DA one-to-one private link between exactly two VPCs
✓ Correct: A. A managed regional hub router for many VPCs and on-prem networks

How to think about it: Transit Gateway = a managed regional hub router connecting many VPCs, VPNs and Direct Connect.

Why A is correct: Each network attaches once to the TGW instead of building a mesh of point-to-point links.

Why the others are wrong:
B) A global edge network that speeds up TCP and UDP traffic to apps — That is AWS Global Accelerator.
C) A load balancer that sends traffic to firewall appliances — That is Gateway Load Balancer.
D) A one-to-one private link between exactly two VPCs — That is VPC peering.

Q2.What is the scope of a single Transit Gateway?
AOne VPC, acting as that VPC's internal router
BRegional; other Regions connect by TGW peering
CGlobal; one TGW attaches VPCs in every AWS Region
DOne Availability Zone, so you deploy one per AZ
✓ Correct: B. Regional; other Regions connect by TGW peering

How to think about it: TGW is regional; to cross Regions you peer TGWs (or use Cloud WAN).

Why B is correct: A TGW lives in one Region, and inter-Region connectivity comes from peering attachments.

Why the others are wrong:
A) One VPC, acting as that VPC's internal router — A TGW is a hub for many VPCs, not part of one VPC.
C) Global; one TGW attaches VPCs in every AWS Region — Cloud WAN gives a global core network; a TGW does not.
D) One Availability Zone, so you deploy one per AZ — TGW is highly available across the Region's AZs.

Q3.Which of the following is a valid Transit Gateway attachment type?
AA CloudFront distribution
BAn AWS Site-to-Site VPN
CAn S3 gateway endpoint
DAn internet gateway (IGW)
✓ Correct: B. An AWS Site-to-Site VPN

How to think about it: TGW attachments: VPC, VPN, Direct Connect gateway, Connect (GRE/SD-WAN), peering.

Why B is correct: VPNs can end directly on a TGW, which also enables ECMP across tunnels.

Why the others are wrong:
A) A CloudFront distribution — CloudFront is an edge service and does not attach to TGW.
C) An S3 gateway endpoint — Gateway endpoints are VPC route-table targets and cannot be TGW attachments.
D) An internet gateway (IGW) — IGWs attach to VPCs, not to Transit Gateways.

Q4.What MTU does Transit Gateway support for traffic between attached VPCs?
A1500 bytes for all traffic
B8500 bytes
C576 bytes
D9001 bytes, the same as inside a VPC
✓ Correct: B. 8500 bytes

How to think about it: TGW MTU: 8500 between VPCs, DX, Connect and peering; 1500 over VPN.

Why B is correct: TGW supports up to 8500 bytes for VPC, DX, Connect and peering traffic; larger packets are dropped.

Why the others are wrong:
A) 1500 bytes for all traffic — 1500 is the limit for VPN attachments, not for VPC-to-VPC traffic.
C) 576 bytes — That is a minimum IPv4 datagram size, not a TGW limit.
D) 9001 bytes, the same as inside a VPC — 9001 is the in-VPC jumbo frame size, but TGW caps at 8500.

Q5.How is Transit Gateway mainly priced?
AFree; you pay only standard data transfer
BA flat monthly fee for each Transit Gateway
CPer attachment-hour plus per GB processed
DA per-route charge in each TGW route table
✓ Correct: C. Per attachment-hour plus per GB processed

How to think about it: TGW cost = per attachment-hour + per GB processed. Peering has no per-attachment fee.

Why C is correct: Every attachment costs per hour, and data sent into the TGW is charged per GB.

Why the others are wrong:
A) Free; you pay only standard data transfer — TGW has its own attachment and processing charges.
B) A flat monthly fee for each Transit Gateway — There is no flat fee; cost scales with attachments and traffic.
D) A per-route charge in each TGW route table — Routes are not billed individually.
TGW BasicsAdvanced
Q6.Two VPCs in the same Region exchange 500 TB per month and need the lowest latency and cost. Everything else uses a Transit Gateway. What is the best choice for this pair?
AKeep it on the TGW and enable appliance mode on both
BUse a Site-to-Site VPN between the two VPCs instead
CAdd a second Transit Gateway just for these two VPCs
DPeer this pair with specific routes; keep TGW
✓ Correct: D. Peer this pair with specific routes; keep TGW

How to think about it: Heavy traffic between just two VPCs = VPC peering (no TGW processing fee, no extra hop). Both can run side by side.

Why D is correct: Peering avoids TGW per-GB charges and the extra hop, and specific peering routes win over the broader TGW route.

Why the others are wrong:
A) Keep it on the TGW and enable appliance mode on both — Appliance mode is for symmetric inspection; it does not cut cost or latency.
B) Use a Site-to-Site VPN between the two VPCs instead — VPN adds overhead and is limited to 1.25 Gbps per tunnel.
C) Add a second Transit Gateway just for these two VPCs — A second TGW still charges per GB processed.
TGW RoutingFundamental
Q7.In Transit Gateway, what does associating an attachment with a TGW route table do?
AIt copies the attachment's CIDRs into that route table
BIt sets which TGW route table its traffic uses
CIt sets the BGP ASN used by the attachment's peers
DIt shares the route table with another AWS account
✓ Correct: B. It sets which TGW route table its traffic uses

How to think about it: Association = which route table an attachment looks up for its outgoing traffic (one per attachment). Propagation = where it advertises its routes.

Why B is correct: Each attachment is associated with exactly one route table, which handles lookups for its packets.

Why the others are wrong:
A) It copies the attachment's CIDRs into that route table — That is propagation, not association.
C) It sets the BGP ASN used by the attachment's peers — ASNs are set on the TGW and the peers, not through association.
D) It shares the route table with another AWS account — Sharing is done with AWS RAM, not association.
TGW RoutingFundamental
Q8.What does route propagation from a VPC attachment do?
AIt limits the attachment to exactly one route table
BIt installs the VPC's CIDRs into chosen TGW route tables
CIt sends the VPC routes to on-premises routers over BGP
DIt adds TGW routes into the VPC's own subnet route tables
✓ Correct: B. It installs the VPC's CIDRs into chosen TGW route tables

How to think about it: Propagation = the attachment's CIDRs are installed automatically in the chosen TGW route table(s).

Why B is correct: Propagated routes save adding static routes and update as CIDRs change.

Why the others are wrong:
A) It limits the attachment to exactly one route table — Limiting to one table is association; an attachment can propagate to many tables.
C) It sends the VPC routes to on-premises routers over BGP — Propagation fills TGW route tables; BGP advertisement to on-premises is a separate step.
D) It adds TGW routes into the VPC's own subnet route tables — VPC subnet route tables still need manual routes that point at the TGW.

Q9.After attaching three VPCs to a TGW with default settings, the VPCs still cannot talk. What is usually missing?
AAn internet gateway and public subnet in every VPC
BA VPC peering connection between each pair of VPCs
CA Direct Connect gateway associated with the TGW
DVPC routes sending other VPCs' CIDRs to the TGW
✓ Correct: D. VPC routes sending other VPCs' CIDRs to the TGW

How to think about it: TGW does not touch VPC route tables: add routes in each VPC's subnet route tables pointing to tgw-xxxx.

Why D is correct: The default TGW route table already propagates VPC routes, but the VPCs themselves must route to the TGW.

Why the others are wrong:
A) An internet gateway and public subnet in every VPC — IGWs are for internet access, not for TGW routing.
B) A VPC peering connection between each pair of VPCs — Peering is not needed; the TGW replaces the mesh.
C) A Direct Connect gateway associated with the TGW — DX gateways are for hybrid links, not VPC-to-VPC traffic.

Q10.What is a blackhole route in a Transit Gateway route table?
AA route whose attachment has been deleted and is waiting to be cleaned up
BA route that sends traffic to the internet
CA route only used if all other routes fail
DA static route that drops traffic matching its destination
✓ Correct: D. A static route that drops traffic matching its destination

How to think about it: Blackhole = match and drop; use it to block traffic, e.g. 10.0.0.0/8 in the egress route table.

Why D is correct: Blackhole routes are an easy way to stop specific VPCs from reaching each other through a shared TGW.

Why the others are wrong:
A) A route whose attachment has been deleted and is waiting to be cleaned up — A deleted attachment can leave routes in blackhole state, but the feature is a deliberate drop route.
B) A route that sends traffic to the internet — TGW has no internet route; egress goes through a NAT gateway in an egress VPC.
C) A route only used if all other routes fail — TGW has no failover-only routes; longest prefix match decides.

Q11.A company wants Prod VPCs and Dev VPCs on one TGW to reach a Shared Services VPC but never each other. How should TGW route tables be set up?
AProd and Dev tables with only Shared routes; Shared gets both
BA separate Transit Gateway for each environment, peered
COne default route table for all, with NACLs blocking Prod-Dev
DAppliance mode on the Prod attachments with a firewall VPC
✓ Correct: A. Prod and Dev tables with only Shared routes; Shared gets both

How to think about it: Segmentation on TGW = separate route tables: Prod RT and Dev RT get only Shared routes; the Shared RT gets both.

Why A is correct: Each group can only look up routes to Shared Services, so Prod and Dev have no path to each other.

Why the others are wrong:
B) A separate Transit Gateway for each environment, peered — This is costly and still needs links to Shared Services.
C) One default route table for all, with NACLs blocking Prod-Dev — Possible but fragile; route-table segmentation is the designed solution.
D) Appliance mode on the Prod attachments with a firewall VPC — Appliance mode is for inspection symmetry, not segmentation.

Q12.A TGW serves 200 VPCs, and an architect wants new spoke attachments to stop joining the full mesh automatically. Which TGW setting should change?
ATurn on auto accept shared attachments for the TGW
BTurn on DNS support on the Transit Gateway itself
CDisable default association and propagation
DLower the TGW's Amazon-side BGP ASN to a private one
✓ Correct: C. Disable default association and propagation

How to think about it: Auto-mesh comes from default route table association and propagation; turn them off for controlled designs.

Why C is correct: New attachments then get no table until you choose one, so nothing is opened by accident.

Why the others are wrong:
A) Turn on auto accept shared attachments for the TGW — This accepts cross-account attachments automatically, which does the opposite of tightening control.
B) Turn on DNS support on the Transit Gateway itself — DNS support helps resolve public names across VPCs; it does not control route tables.
D) Lower the TGW's Amazon-side BGP ASN to a private one — The ASN has no effect on route table association.

Q13.When you attach a VPC to a TGW, what do you choose for each Availability Zone?
AEvery subnet that exists in that AZ
BAn Elastic IP for the TGW in that AZ
CA route table to share with the TGW
DOne subnet, for the TGW's ENI
✓ Correct: D. One subnet, for the TGW's ENI

How to think about it: One subnet per AZ (a small dedicated /28 is best practice); the TGW puts an ENI there.

Why D is correct: That subnet's ENI serves the whole AZ, so a small dedicated /28 keeps IPs free for workloads.

Why the others are wrong:
A) Every subnet that exists in that AZ — Only one subnet per AZ is chosen, though all subnets in that AZ can then use it.
B) An Elastic IP for the TGW in that AZ — TGW attachments use private IPs only.
C) A route table to share with the TGW — Route tables are configured separately; the attachment asks for subnets.

Q14.Instances in an AZ where the VPC's TGW attachment has no subnet cannot reach the TGW. Why?
ASecurity groups block cross-AZ TGW traffic by default
BThat AZ's route table points to a different TGW
CTGW only supports two AZs per VPC attachment
DThe attachment has no TGW ENI in that AZ
✓ Correct: D. The attachment has no TGW ENI in that AZ

How to think about it: No attachment subnet in an AZ = no TGW ENI in that AZ = workloads there cannot use the TGW.

Why D is correct: Enable every AZ that has workloads by choosing a subnet there in the attachment.

Why the others are wrong:
A) Security groups block cross-AZ TGW traffic by default — Security groups do not have AZ-aware defaults.
B) That AZ's route table points to a different TGW — Route tables are per subnet, not per AZ, and the root cause is the missing ENI.
C) TGW only supports two AZs per VPC attachment — You can enable every AZ the VPC uses.

Q15.What does Transit Gateway appliance mode do on a VPC attachment?
AIt encrypts traffic between the TGW and the VPC
BIt pins both directions of a flow to one appliance AZ
CIt lets the attachment use public IP addresses
DIt raises the attachment's bandwidth for heavy traffic
✓ Correct: B. It pins both directions of a flow to one appliance AZ

How to think about it: Appliance mode = flow symmetry: both directions of a flow go to the same AZ's appliance. Needed for stateful firewalls.

Why B is correct: Without it, TGW keeps traffic in its source AZ, so return traffic can reach a different firewall that never saw the original packet.

Why the others are wrong:
A) It encrypts traffic between the TGW and the VPC — TGW attachments are not encrypted by this setting.
C) It lets the attachment use public IP addresses — Attachments remain private, whatever the mode.
D) It raises the attachment's bandwidth for heavy traffic — Appliance mode is about symmetry, not throughput.

Q16.A central inspection VPC with stateful firewalls in two AZs randomly drops return traffic between spoke VPCs in different AZs. What is the fix?
AMove all spoke workloads into one Availability Zone
BAdd a NAT gateway in each spoke VPC's subnets
CEnable appliance mode on the inspection attachment
DTurn on cross-zone load balancing in the spoke VPCs
✓ Correct: C. Enable appliance mode on the inspection attachment

How to think about it: Stateful inspection through TGW + asymmetric drops = turn on appliance mode on the inspection VPC attachment.

Why C is correct: TGW then hashes each flow to a single AZ in the inspection VPC, so both directions see the same firewall.

Why the others are wrong:
A) Move all spoke workloads into one Availability Zone — This hurts availability and does not fix the underlying routing.
B) Add a NAT gateway in each spoke VPC's subnets — NAT does not make TGW flows symmetric.
D) Turn on cross-zone load balancing in the spoke VPCs — Spoke VPCs have no such setting; the problem is at the TGW attachment.

Q17.A TGW owned by a network account is shared with workload accounts. Engineers worry that "us-east-1a" may not mean the same place in each account. What should they use when planning attachment subnets?
AAZ names such as us-east-1a, shown in each console
BThe subnet CIDR blocks chosen in each account
CThe TGW's ASN and the attachment's resource ID
DAZ IDs such as use1-az1, same in every account
✓ Correct: D. AZ IDs such as use1-az1, same in every account

How to think about it: Across accounts, AZ names are shuffled. Use AZ IDs such as use1-az1.

Why D is correct: AZ names are mapped differently per account, while AZ IDs are consistent.

Why the others are wrong:
A) AZ names such as us-east-1a, shown in each console — These can point to different physical AZs in different accounts.
B) The subnet CIDR blocks chosen in each account — CIDRs say nothing about physical AZ location.
C) The TGW's ASN and the attachment's resource ID — ASNs are for BGP, not for identifying AZs.

ARoutes learned from the VPC route tables on both sides

Q22.An SD-WAN appliance in a VPC needs about 15 Gbps to the TGW through a Connect attachment. Each GRE tunnel (Connect peer) carries up to 5 Gbps. How do you get the bandwidth?
AAdd Connect peers advertising the same prefixes
BReplace the Connect attachment with a TGW peering
CRaise the MTU of the single GRE tunnel to 9001 bytes
DTurn on appliance mode on the transport attachment
✓ Correct: A. Add Connect peers advertising the same prefixes

How to think about it: Connect: 5 Gbps per GRE peer, up to 4 peers per attachment; ECMP across peers by advertising the same prefixes.

Why A is correct: Multiple Connect peers advertising identical prefixes let the TGW spread flows across tunnels for more bandwidth.

Why the others are wrong:
B) Replace the Connect attachment with a TGW peering — Peering connects TGWs, not SD-WAN appliances.
C) Raise the MTU of the single GRE tunnel to 9001 bytes — A bigger MTU does not raise the per-tunnel bandwidth cap, and TGW tops out at 8500 bytes.
D) Turn on appliance mode on the transport attachment — Appliance mode controls flow symmetry, not bandwidth.

Q23.A Site-to-Site VPN tunnel to a TGW carries up to about 1.25 Gbps. How can more VPN bandwidth be reached?
AEnd the VPN on a virtual private gateway instead
BSeveral VPN connections to the TGW with BGP and ECMP
CUse static routing on a single VPN connection
DRaise the VPN tunnel MTU to 8500 bytes for each tunnel
✓ Correct: B. Several VPN connections to the TGW with BGP and ECMP

How to think about it: VPN to TGW + BGP + ECMP across several tunnels and connections; a VGW does not support ECMP.

Why B is correct: TGW spreads flows across equal-cost tunnels, which adds up the bandwidth.

Why the others are wrong:
A) End the VPN on a virtual private gateway instead — A VGW does not support ECMP, so it is held to one active tunnel's bandwidth.
C) Use static routing on a single VPN connection — Static routing on one connection gives no extra throughput.
D) Raise the VPN tunnel MTU to 8500 bytes for each tunnel — VPN traffic is limited to 1500 bytes and MTU does not lift the cap.

Q30.In a central egress design, the egress VPC's attachment route table has 0.0.0.0/0 to the egress VPC, and spokes are now reaching each other through it. What prevents this?
ATurn on appliance mode on the egress attachment
BAssociate the spokes with the egress VPC's route table
CDelete the internet gateway from the egress VPC
DBlackhole 10.0.0.0/8 in the spoke route table
✓ Correct: D. Blackhole 10.0.0.0/8 in the spoke route table

How to think about it: Stop spoke-to-spoke via the default route = blackhole the private ranges (e.g. 10.0.0.0/8) in the spoke route table.

Why D is correct: The more-specific blackhole wins over 0.0.0.0/0, so spoke-to-spoke traffic is dropped.

Why the others are wrong:
A) Turn on appliance mode on the egress attachment — Appliance mode makes flows symmetric; it does not block them.
B) Associate the spokes with the egress VPC's route table — Spokes would then learn more routes, not fewer.
C) Delete the internet gateway from the egress VPC — That breaks internet access and does nothing about spoke traffic.

ADirectly from the TGW to the GWLB with no endpoint
BThrough an Application Load Balancer before the firewalls
CThrough VPC peering between the TGW and the GWLB VPC
DThrough a GWLB endpoint in the inspection VPC
✓ Correct: D. Through a GWLB endpoint in the inspection VPC

B) Through an Application Load Balancer before the firewalls — ALBs work at layer 7 and cannot carry all IP traffic transparently.

Q32.How can one Transit Gateway be used by VPCs in many AWS accounts?
